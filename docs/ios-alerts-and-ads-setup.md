# iOS Alerts + Ads — the portal steps

The code for both is written and wired up. Everything below is a
**developer-portal action**, which is James's job — nothing here can or
should be driven from a script.

Until these are done the app still builds, installs and runs completely
normally: alerts are simply inert and the banner shows Google's sample ads.
That's deliberate — both subsystems degrade to no-ops rather than crashing,
the same way the backend does when `FIREBASE_SERVICE_ACCOUNT` is unset.

---

## A. Alerts — three steps

### A1. Register the iOS app in the existing Firebase project

Firebase console → the project already used for Android → Add app → **iOS**.

- **Bundle ID:** `com.nbawatchability.app` (same as the Android package name
  coincidentally is not — it must be exactly this string, from
  `PRODUCT_BUNDLE_IDENTIFIER` in `ios/project.yml`)
- **App nickname:** anything, e.g. "Big4 Watchability iOS"
- **App Store ID:** skip, it can be added later

Download the generated **`GoogleService-Info.plist`** and send it to me. It
goes in `ios/Big4Watchability/Resources/` and I'll wire it into
`project.yml`'s sources.

> Until that file exists in the bundle, `PushNotificationManager` never
> calls `FirebaseApp.configure()` at all and logs
> `"GoogleService-Info.plist not in bundle - alerts are inert until it is"`.
> That check is load-bearing: `FirebaseApp.configure()` hard-crashes on a
> missing plist, so without it the app would die at launch.

### A2. Create an APNs auth key and upload it to Firebase

Apple Developer portal → Certificates, Identifiers & Profiles → **Keys** →
**+**

- Name it something like "Big4 Watchability APNs"
- Tick **Apple Push Notifications service (APNs)**
- Continue → Register → **Download the `.p8`**

⚠️ **Apple lets you download a `.p8` exactly once.** Save it somewhere you
won't lose it. Also note the **Key ID** (shown on that page) and your
**Team ID** (top-right of the developer portal).

Then: Firebase console → Project settings → **Cloud Messaging** → under the
iOS app, **APNs Authentication Key** → Upload, and give it the `.p8`, the
Key ID and the Team ID.

One key covers development *and* production, and every app under the team —
so this is a one-time job even if more apps follow.

### A3. Turn on the Push Notifications capability

Apple Developer portal → Identifiers → `com.nbawatchability.app` → tick
**Push Notifications** → Save.

The matching `aps-environment` entitlement is already generated by
`ios/project.yml`, so nothing is needed on my side for this.

**Then it works.** No backend change is needed at all — iOS registers with
APNs, Firebase swaps that for an FCM token, and that token lands in the same
`alert_devices.fcm_token` column Android already uses, going out through the
same poller.

## B. Ads — two steps

### B1. Register an iOS app in the existing AdMob account

AdMob console → Apps → **Add app** → **iOS** → the app is *not* yet on the
App Store, so choose "No" when asked if it's listed (you can link it to the
App Store listing later, once it's live).

This gives you an **iOS App ID** of the form
`ca-app-pub-6295039345620062~XXXXXXXXXX`.

### B2. Create a banner ad unit

In that new iOS app → Ad units → **Add ad unit** → **Banner** → name it
something like "iOS anchored banner".

This gives you an **ad unit ID** of the form
`ca-app-pub-6295039345620062/XXXXXXXXXX`.

Send me both IDs. They replace two values:

| Value | Where it lives |
|---|---|
| iOS App ID (`~`) | `INFOPLIST_KEY_GADApplicationIdentifier` in `ios/project.yml` |
| Banner unit ID (`/`) | `AdUnit.banner` in `ios/.../Ads/AdBannerView.swift` |

> **Ad unit IDs are per-platform.** Android's real IDs
> (`...~3445511248` / `...​/5400756591`) cannot be reused here. Until B1/B2
> are done the app ships Google's official **test** IDs, which serve real
> sample ads, are explicitly safe in production, and earn nothing — exactly
> how Android shipped v3 before v4 swapped in the real ones on 2026-09-16.

No separate payment setup is needed: the AdMob account's payments were
already sorted during the Android launch.

## C. App Store Connect — the privacy label has to change

**This one is not optional and it is easy to forget.**

The iOS app's privacy nutrition label is currently **"Data Not Collected"**,
which was accurate when `ios/` contained no Firebase, no AdMob and no
tracking code at all. It is no longer accurate. Submitting with the old
label is a misrepresentation Apple does reject for.

App Store Connect → the app → **App Privacy** → Edit. What now has to be
declared:

| Data type | Used for | Linked to identity? | Tracking? |
|---|---|---|---|
| **Device ID** (advertising identifier) | Third-Party Advertising, Analytics | No | **Yes** |
| **Product Interaction** | Analytics | No | No |
| **Coarse Location** (AdMob may infer from IP) | Third-Party Advertising | No | Yes |

Declaring anything as **Tracking: Yes** is what obliges the app to show the
App Tracking Transparency prompt — which the UMP SDK already presents as
part of the consent flow, and whose prompt copy is set by
`INFOPLIST_KEY_NSUserTrackingUsageDescription` in `ios/project.yml`.

Google publishes its own current list of what the Mobile Ads SDK collects;
worth a glance before filling the form in, as it does shift between SDK
versions.

The **privacy policy is already updated** (`docs/privacy-policy.html`, now
dated 2026-09-21) — ads and push are described for both platforms, the ATT
prompt is explained, and it now also discloses that the favorites list is
sent to the server as part of alert registration, which the old wording had
never mentioned on either platform.
